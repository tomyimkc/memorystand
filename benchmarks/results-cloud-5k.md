# 5,000 memories on CockroachDB Cloud (Basic, AWS us-west-2)

Run from a laptop in Hong Kong against a managed cluster in Oregon. **Read the latency
numbers below as a measurement of the Pacific, not of CockroachDB.**

## What this run establishes

- The vector index **is used on CockroachDB Cloud Basic**: `vector search` + `prefix spans`
  on the real `recall()` query shape. That was the single biggest unproven assumption in
  the project, and it is now settled on managed infrastructure rather than Docker.
- `SET CLUSTER SETTING feature.vector_index.enabled` is **rejected** on Basic — and is not
  needed. The index works without it.
- The Cloud GC window is **4,500s (75 min)**, not the 14,400s a local single node defaults
  to. Time-travel replay is bounded correspondingly tighter in production.

## Why the latency looks bad, honestly

| | p50 | p95 | p99 |
|---|---|---|---|
| vector-indexed, from Hong Kong | 333.28 ms | 651.43 ms | 903.00 ms |
| brute force, same data | 466.07 ms | 750.65 ms | 1206.48 ms |

Only **1.4x** apart, versus 76x on a local 3-node cluster at 250k rows. Nothing regressed:
a trans-Pacific round trip is roughly 150-200 ms, so RTT dominates and the index advantage
is buried underneath it. Write throughput (45 rows/sec vs 4,093 locally) is the same story.

This is the correct argument for the deployed topology: the Lambda runs **in us-west-2,
beside the cluster**, where RTT is sub-millisecond and the index advantage reappears. A
benchmark run across an ocean measures the ocean. Quoting these figures as CockroachDB's
performance would be wrong, and quoting the local ones as production performance would be
equally wrong — which is why both are published, each labelled with what it actually is.

## Environment

- CockroachDB: `CockroachDB CCL v26.2.1 (x86_64-pc-linux-gnu, built 2026/05/21 21:07:32, go1.25.5)`
- Seeding path: direct SQL insert, bypassing `backend.memory.remember`'s
  admission control (contradiction checks, embedding-neighbour comparison).
  This is intentional -- this harness measures **recall latency**, not the
  write-time adjudication cost. Every seeded row is written with
  `verdict='accepted'` by hand so it is actually recallable.
- Embeddings: `backend.embeddings.embed`, deterministic local stub (MEMORYSTAND_EMBED_STUB=1, no AWS account used).
- `agent_memories`: the real, already-deployed table from `db/schema.sql`,
  with its `VECTOR INDEX agent_memories_tenant_idx (tenant_id, verdict, embedding
  vector_cosine_ops)`.
- `agent_memories_noindex`: created by this script with an identical column set and
  the exact same generated rows (same `memory_id`, same embedding) as
  `agent_memories`, with **no vector index** -- the apples-to-apples control.
- Rows seeded this run: 5000 per table, tagged
  `source='memorystand-loadtest'` in `agent_memories` (used for isolation and
  cleanup). `agent_memories` total row count at measurement time:
  5101 (may include rows from other concurrent work on this
  shared cluster -- see caveat below). `agent_memories_noindex` total row count:
  5000.
- Tenants: 20. Batch size: 75 rows per INSERT
  statement (never one giant multi-row INSERT).

## Optimizer plan choice

The optimizer **did** choose the vector index for the production query shape --
the exact query `backend.memory.recall()` issues. The `vector search` node and
the `prefix spans` line above come from this run, not from a contrived probe.

`prefix spans` is the part worth reading closely: the scan is bounded to one
tenant's *admitted* memories, because the index prefix is
`(tenant_id, verdict, embedding)`. ANN cost therefore scales with that tenant's
own row count rather than the whole table's, and a held-for-review memory is not
merely filtered out of the result -- it is not in the partition being searched.

Two things had to be true for this plan to appear, both learned the hard way: the
filter columns must sit inside the index prefix, and `ANALYZE` must have run since
the last bulk load. Miss either and the optimizer silently falls back to a scan.


## Caveats

- Single run, not repeated across seeds. Topology: managed CockroachDB Cloud Basic,
  AWS us-west-2, driven trans-Pacific (see the correction note above).
- This cluster may be shared with other concurrent local development at
  measurement time; latency numbers can carry noise from that, not just
  from the index/no-index difference.
- Seeding bypasses `backend.memory.remember`'s admission control by design
  (see above) -- this measures retrieval, not the full write path.
- Percentiles are computed from 200 samples per table; at low
  `--quick` row counts the vector index has less to prune and the gap will
  be smaller and noisier than at the full default row count (10000).
- This is a shared local cluster with other concurrent agents/processes
  writing to `agent_memories` during this run. The harness transparently
  retries two specific, expected transient errors with backoff: SQLSTATE
  40001 (`SerializationFailure`, CockroachDB's documented SERIALIZABLE
  conflict-and-retry contract -- see `backend/db.py`) from write
  contention, and `psycopg2.InternalError: remote wall time is too far
  ahead (...) to be trustworthy`, a Docker Desktop VM clock-drift artifact
  under concurrent host load (also observed on plain non-vector
  statements, so it is not a defect in the vector index or this script).
  Retried attempts are excluded from the timed recall-latency samples
  above so contention/infra noise cannot masquerade as a slow query.
  Transient retries observed this run: **0**.
